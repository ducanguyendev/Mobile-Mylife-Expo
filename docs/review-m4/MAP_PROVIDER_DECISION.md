# Native provider decision

Selected **`@vietmap/vietmap-gl-react-native` exactly `3.0.0`**, installed through `npx.cmd expo install`, with SDK58 `expo-dev-client`. No Google Maps dependency or WebView was added. `app.json` carries the provider config plugin; prebuild generates ignored Android/iOS projects. Android/ios scripts now request native builds. Native build and runtime outcomes are recorded separately in NATIVE_SMOKE_RESULTS.md.

Evidence researched 11 November 2026:

- [VIETMAP official Expo guidance](https://maps.vietmap.vn/docs/sdk-mobile/react-native/expo-map/): native SDK requires a development build; tilemap keys may ship in the app with restrictions; service/geocoding keys stay on Backend. Its embedded 0.0.6/navigation5/gesture1 examples were not adopted.
- [VIETMAP package/source](https://github.com/vietmap-company/vietmap-gl-react-native): registry latest3.0.0; inspected published README migration v2→v3, package.json, Fabric specs, Android Gradle and iOS config plugin. Tarball SHA1 `2f3da4a849a95fa1c86f07519f4be80d9335ee59`.
- Published v3 requires Android New Architecture, minAPI24, compiledAPI35, iOS15.1 minimum following RN; peers RN>=0.74, React>=18.2 and optional Expo config-plugins>=7. It declares testing against RN0.76.x, **not an Expo58/RN0.88 certification**. Actual compile/runtime evidence is necessary. Native Android SDK4.1.0 and JitPack artifacts are declared by the package; no native SDK version was forced.
- [Expo58 reference](https://docs.expo.dev/versions/v58.0.0/) and [development builds](https://docs.expo.dev/develop/development-builds/introduction/): Expo Go is insufficient. Generated SDK58 project uses Fabric and compile/target37; intended runtime coverage is Android35. Do not downgrade to API35/old Expo merely to fit documentation.

VIETMAP supports MapView/Camera/PointAnnotation, gesture pan/pinch, press coordinates, style switching and camera bounds. UI uses official `maps/styles/lm` and `dm` endpoints matching Web W10. Saved/pending points are distinct; locations use server group keys/counts. Attribution/logo remain enabled. Camera fitting happens once after first data/native load or explicit Fit; polling does not repeatedly recenter. Selected group changes focus deliberately. Mercator camera bounds cap display latitude at85; stored/list coordinates retain their exact valid ±90 range.

Only `EXPO_PUBLIC_VIETMAP_TILE_KEY` is accepted, intentionally public and documented in `.env.example`. Use a disposable/restricted mobile tilemap key for provider QA. Never copy Backend services credentials. No key values are stored in reports, hardcoded, or printed. SDK JS logger consumes messages because they can include style URLs. No GPS/UserLocation component or location permission is requested; address text never becomes a guessed pin. Backend performs geocoding.

Fallback feasibility: registry MapLibre RN11.5.1 peers Expo>=54, RN>=0.80, React>=19.1; [official setup](https://maplibre.org/maplibre-react-native/docs/setup/getting-started/) and [Expo plugin](https://maplibre.org/maplibre-react-native/docs/setup/expo/) support new architecture/development builds. It is a plausible alternative engine if VIETMAP compilation/runtime proves incompatible. A public tile key does not by itself prove contractual permission to use every VIETMAP style through a different engine; confirm account/style terms and attribution before adoption. No alternate engine was silently substituted or claimed tested.

Executed compatibility evidence: Android x86_64 custom SDK58/RN0.88 development APK builds and initializes VIETMAP on Android15/API35. Published v3 ESM specs lose NativeProps types required by RN0.88 Babel codegen; initial native runtime failed before loading MapView. A scoped [Expo Metro resolver](https://docs.expo.dev/guides/customizing-metro/) maps only this package to its shipped TS entry, matching its own native codegen sources. The regression parses the actual TypeScript spec and reproduces the published-JS rejection. All other modules use Expo's default resolver; no global exports switch, library patch, downgrade or alternate provider. Actual dark tiles, count annotations, marker selection and tile-backed tap picker are visible in the native evidence. This is observed Android compatibility, not general iOS/physical-device certification.

The existing Web public tile key was used for synthetic QA only after explicit user approval resolved the automatic-review credential-egress block. Both intended style endpoints returned200; actual tile rendering was verified independently on native. Values never entered tracked files/reports. Production mobile key restrictions, quotas and signing/package setup remain open; `.env.example` stays blank. Initial invalid-key failure evidence is retained.
