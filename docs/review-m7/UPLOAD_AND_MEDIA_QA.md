# Upload and media QA

Automated PASS: M7 tests exercise repeated native File parts, all batch metadata fields, raw photo arrays, no manual multipart Content-Type, picker cancellation, review selection, zero/21 files, invalid MIME/extension/URI/filename/size, false signatures and pre-dispatch cancellation. Real Kestrel/PostgreSQL confirms two-file multipart persistence and rejects HEIC, bad signatures, wrong extensions,21 files and >5MiB with400. Adapter checksum failure502 preserves existing records.

The picker accepts images, multiple selection, no editing/conversion, original quality, no EXIF, maximum20. Unsupported HEIC/HEIF is rejected clearly; it is never renamed to JPEG. Selection can be reviewed/removed/canceled. Missing filename/MIME is rejected rather than guessed. File bytes and size are inspected sequentially, first12 bytes only for signatures; Backend performs its full independent checks. FormData retains File references rather than eagerly copying all bytes into JS arrays.

Native format policy uses existing SDK58 File/FormData architecture validated for avatars in M3. The M7 upload transport itself must also be proven in the current native run; inherited M3 evidence alone is not M7 native PASS. No invented percentage progress is displayed: only upload-in-progress, then server-confirmed authoritative state. Native device results are tracked separately in NATIVE_SMOKE_RESULTS.

Background cancels/ignores network work and hides private gallery/lightbox. An in-progress system picker may background the app: its editor stays mounted for the same account so the selection can return, while write dispatch remains inactive. Navigation/account changes unmount it and reject stale picker results. Process-death pending-picker recovery is NOT IMPLEMENTED for M7; users must reselect, with no automatic upload. This is distinct from M3's persisted target-only recovery.

Uncertain dispatch locks writes until explicit reconciliation, clears submitted selections, and tells the user to inspect persisted photos before selecting again. No automatic retry after timeout/5xx;429 carries Retry-After and the mutation gate blocks early redispatch. Cancel before dispatch is safe; an OS/background abort after dispatch cannot prove provider cancellation/rollback. The existing15-second API timeout can make large/slow batches uncertain; use smaller reviewed batches and retain this performance/transport gate for release.

Native QA found a concrete SDK58 compatibility defect in the initial signature-read path: File.slice constructs a global Blob from a typed array, incompatible with the existing client's React Native Blob. Initial native submission failed before persistence (API check retained125 total /0 in the new album). It was replaced by native File.open(FileMode.ReadOnly), async readBytes(12), and finally close. Browser File retains its normal slice/arrayBuffer path. The regression adapter now deliberately throws on native slice, so a browser-only mock cannot conceal this again. The current client is reloaded before the corrected native submission; final outcome is in NATIVE_SMOKE_RESULTS.

Private images use the binary API mode, refresh/session guards, bounded account-local queue, ephemeral data URI, no disk cache and bounded retry. Native GIF animation, HEIC selection behavior on iOS, very large decoded images, physical memory and long-session provider throttling are NOT TESTED unless separately recorded.
